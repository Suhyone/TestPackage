# แผนการทำงาน + จำลองการใช้งานหน้างาน (Field Usability Plan)

เป้าหมาย: คนหน้างานใช้แล้ว **งงน้อย กดน้อย ไม่ต้องกรอกซ้ำ** — ทำงานหลักให้จบในไม่กี่ขั้น บนมือถือ มือเปื้อน แดดจ้า สัญญาณไม่ดี

> **ที่มาของตัวเลข:** จำนวนการกด/ขั้นตอนด้านล่างนับจากการอ่านโค้ด (`punch_add.js`, `punch_detail.js`, `tp_pretest.js`, `qc_list.js`, `add_modal.php`) — **ไม่ใช่การสังเกตผู้ใช้จริง** และยังไม่ได้เปิดดูหน้าจริงหลังล็อกอิน ต้องยืนยันด้วยการทดลองหน้างานตามหัวข้อ 6 ก่อนสรุปว่าแก้ได้ผลจริง

---

## 1. ผู้ใช้และสถานการณ์หน้างาน

| ผู้ใช้ | บริบท | งานหลักที่ต้องจบเร็ว |
|---|---|---|
| **QC (QA/QC Inspector)** | เดินตรวจท่อ/ISO ในไซต์ ถือมือถือมือเดียว ใส่ถุงมือ | บันทึกตำหนิ + ถ่ายรูป · ตรวจงานแก้ ปิด/ตีกลับ · ตอบ Pre-test |
| **Officer (ช่าง/หัวหน้างานแก้)** | ได้รับงานแก้ ทำงานกลางแจ้ง | ดูว่าต้องแก้อะไร → แก้ → ถ่ายรูป → ส่ง |
| **Admin / QC ออฟฟิศ** | โน้ตบุ๊ก ตั้งค่า ตรวจภาพรวม พิมพ์รายงาน | ดูสถานะ pack, ผู้ใช้, Export/พิมพ์ |
| **Viewer (ลูกค้า CIMTAS ถ้าอนุมัติ)** | เปิดดูอย่างเดียว | ดูสถานะ pack/punch, รายงาน |

เงื่อนไขหน้างานที่ต้องออกแบบรองรับ: แดดจ้า (contrast สูง), ถุงมือ (ปุ่มใหญ่ ≥ 44px), สัญญาณขาด ๆ หาย ๆ, มือถือหลายรุ่น (Android/iOS), พิมพ์ไทย/อังกฤษบนมือถือช้า

## 2. จำลองการใช้งาน (Walkthrough) + นับขั้นตอน

### สถานการณ์ A — QC เจอตำหนิ 1 จุด ที่ท่อ (บันทึก punch)
ขั้นตอนปัจจุบัน (มือถือ):
1. เปิดเว็บ/ล็อกอิน (ถ้า session หมด) → เมนู → Punch List
2. กด **Add Punch Item**
3. พิมพ์/เลือก **Test Package No.** (datalist พิมพ์ค้น)
4. เลือก **Drawing** (หรือพิมพ์ใหม่)
5. เลือก **Category** (ค่าเริ่ม "—")
6. Discipline (ค่าเริ่ม Piping)
7. พิมพ์ **Description**
8. กดเพิ่มรูป → ถ่าย (1–N ครั้ง)
9. กด **Save**
→ **ราว 8–10 การกด/กรอก** ต่อ 1 ตำหนิ

**จุดที่ติด**
- Test Package No. และ Drawing ต้องกรอกใหม่ **ทุกครั้งที่เปิดฟอร์ม** (`openAdd()` ล้างค่าหมด) ทั้งที่เดินตรวจ pack เดียวกันต่อเนื่อง
- Category ไม่บังคับ — บันทึกได้โดยไม่เลือก ทั้งที่ Category A/B คือหัวใจของกฎ gate (ข้อมูลจะไม่มีผลต่อ gate)
- พิมพ์ Description ซ้ำ ๆ แบบเดิม (เช่น "Missing gasket", "Support not welded") บนมือถือช้า
- ถ้าอยู่ในหน้า pack อยู่แล้ว (Test Package Detail) ยังต้องไปหน้า Punch List แล้วเลือก pack ใหม่ (ไม่ได้ prefill — ต้องตรวจในโค้ดของลิงก์ `?tp=` ว่า Add รับค่าไหม)
- ฟอร์มเปิดเป็น modal ยาว มีช่อง "Or new Drawing" วางคู่กับ select — คนใหม่อาจงงว่าต้องกรอกอันไหน

### สถานการณ์ B — QC เจอตำหนิ 10 จุดใน Drawing เดียว
- ฟอร์มรองรับหลายการ์ด + "Add another item" คัดลอก Category/Discipline จากใบก่อน (ดี)
- แต่ **รูปต้องถ่ายต่อการ์ด** และเลื่อนฟอร์มยาวมาก; ถ้าสัญญาณหลุดตอน Save ทั้งชุด (10 ตำหนิ + รูป) อาจเสียงานทั้งหมด ไม่มี draft
- หลัง Save ฟอร์มปิด ต้องเปิดใหม่และกรอก pack/drawing ใหม่ถ้าจะเก็บ Drawing ถัดไป

### สถานการณ์ C — Officer แก้งานแล้วส่ง
1. ล็อกอิน → Punch List (เห็นเฉพาะงานที่ได้รับ ตามออกแบบ)
2. หาแถวที่ต้องแก้ (กรอง/ค้นหา/เลื่อน)
3. แตะแถว → เปิดแผงรายละเอียด
4. ถ่ายรูปหลังแก้
5. พิมพ์โน้ต (ไม่บังคับ)
6. กด **Submit Fix** (ถ้าไม่มีรูปมี confirm)
→ **ราว 5–6 ขั้นต่อ 1 รายการ** และ **ต้องทำทีละรายการ** — แก้ 15 จุดใน pack เดียวต้องวนซ้ำ 15 รอบ
- สถานะยังเป็น Open หลังส่งงาน (ตามฟอร์ม) → ในตารางแยกไม่ออกว่า "แก้แล้วรอ QC" กับ "ยังไม่ได้แก้" (ต้องเปิดแผงดู History) — ทั้งสองฝ่ายเสียเวลา

### สถานการณ์ D — QC ตรวจงานแก้ แล้วปิด/ตีกลับ
1. Punch List → หาแถวที่ "แก้แล้ว" (แยกไม่ออกจากตาราง ดูข้างบน)
2. แตะแถว → ดูรูปก่อน/หลัง
3. กด **Close Item** → **confirm** (เพิ่มในรอบแก้ QA) → หรือ **Reject Fix** (พิมพ์โน้ต)
→ **3–4 ขั้นต่อรายการ** ปิด 20 รายการ = ~70 การกด
- confirm ที่เพิ่มเพื่อกันกดพลาด **แลกกับการกดเพิ่ม** — ปิดแล้ว Reopen ได้ จึงควรใช้ "Undo" แทน confirm (ดูข้อ 4.5)

### สถานการณ์ E — QC ตอบ Pre-test Checklist (30 ข้อ)
- 1 คลิกต่อข้อ บันทึกทันที (ดี) → ขั้นต่ำ 30 คลิก ต่อ pack · ส่วนใหญ่คำตอบคือ YES
- ไม่มีปุ่ม "ตั้งทั้งหมดเป็น YES" / "YES ทั้งหมวด" — pack ละ 30 คลิก × 58 pack
- ข้อที่ตอบ NO สร้าง punch A อัตโนมัติ (ดี ลดงานซ้ำ) แต่หลังปิด punch ต้องไปแก้คำตอบเป็น YES/N/A ด้วยมือ (2 ที่ ต้องทำเอง)

### สถานการณ์ F — QC / PM เช้านี้อยากรู้ว่า pack ไหนพร้อมทดสอบแรงดัน
- Register มีชิปสถานะ + ตัวกรอง (ดี) แต่ไม่มีมุมมอง "พร้อมทดสอบ" ที่รวม pre-test + punch A
- Pressure test ยังไม่มี → ต้องดูหลายแท็บประกอบกัน

### สถานการณ์ G — สัญญาณขาด/แบตหมดกลางทาง
- ไม่มีโหมดออฟไลน์/คิว: ถ้ากด Save ตอนสัญญาณหลุด ข้อมูล+รูปหาย (ต้องพิมพ์/ถ่ายใหม่) · ผู้ใช้จะเห็นข้อความ error ที่อ่านรู้เรื่อง (`friendlyErr`) แต่ยังต้องทำใหม่

## 3. ภาพรวมจุดที่ใช้ยาก (เรียงตามผลกระทบ)

| # | ปัญหา | ผลต่อผู้ใช้ | ที่มา |
|---|---|---|---|
| 1 | ฟอร์มเพิ่ม punch ไม่จำ Pack/Drawing ล่าสุด | กรอกซ้ำทุกตำหนิ | `openAdd()` ล้างค่า |
| 2 | Category ไม่บังคับ | punch A/B ผิด/หายจาก gate | `saveAdd()` ยอม null |
| 3 | แก้/ปิดได้ทีละรายการ ไม่มีทำเป็นชุด | งานซ้ำเป็นสิบรอบ | `punch_detail.js` |
| 4 | แยก "แก้แล้วรอตรวจ" จาก "ยังไม่แก้" ในตารางไม่ได้ | QC/Officer ต้องเปิดดูทีละแถว | สถานะ Open ทั้งคู่ |
| 5 | Pre-test ไม่มี "YES ทั้งหมด" | 30 คลิกต่อ pack | `tp_pretest.js` |
| 6 | ไม่มี draft/คิวออฟไลน์ | เสียงานเมื่อสัญญาณหลุด | ไม่มีใน `punch_add.js` |

| 8 | confirm ก่อน Close Item | กดเพิ่มทุกรายการ | `punch_detail.js` |
| 9 | ไม่มีทางลัดจาก pack → "เพิ่ม punch ของ pack นี้" | ย้ายหน้า + เลือก pack ใหม่ | ต้องตรวจ `?tp=` |
| 10 | ตาราง qc_list ใช้คีย์บอร์ดยาก (900 tab stop), ช่องค้นหาไม่มี label | a11y/ใช้บนโน้ตบุ๊กช้า | ค้างจาก QA รอบ 2 |

## 4. วิธีลดขั้นตอนซ้ำ (ข้อเสนอ เรียงตามคุ้มค่า)

**4.1 จำ Pack / Drawing / Category ล่าสุด และปุ่ม "Save & add another"** *(ผลสูง · งานน้อย)*
เปิดฟอร์มครั้งถัดไป prefill Pack+Drawing ล่าสุด (เก็บใน `localStorage` ต่อผู้ใช้); เพิ่มปุ่ม **Save & add another** คงค่า Pack/Drawing/Category/Discipline เคลียร์เฉพาะ Description+รูป → ตำหนิที่ 2 เหลือ ~3 ขั้น (พิมพ์ + ถ่าย + Save)

**4.2 เปิดฟอร์มจาก pack โดย prefill** *(ผลสูง · งานน้อย)*
ปุ่ม **Add punch** ในหน้า Test Package > Punch ส่ง `?tp=…&add=1` → เปิดฟอร์มพร้อม pack นั้น (และ Drawing ล่าสุด)

**4.3 บังคับ Category + ปุ่มเลือกเร็ว** *(ผลสูง · งานน้อย)*
เปลี่ยน Category เป็น **ปุ่มเลือก A / B ใหญ่ ๆ** (ไม่ใช่ dropdown) พร้อมคำอธิบายสั้นใต้ปุ่ม ("A = ห้ามทำงานต่อ") และ **ห้าม Save ถ้ายังไม่เลือก**

**4.4 ตำหนิสำเร็จรูป (Quick picks)** *(ผลปานกลาง · งานปานกลาง)*
ปุ่ม chip ใต้ช่อง Description จากรายการยอดนิยมของโครงการ (ดึงจากข้อมูลเดิม 181 รายการ หรือ master data) แตะเพื่อเติม แล้วแก้ต่อได้

**4.5 Undo แทน confirm ของ Close Item / Reopen** *(ผลปานกลาง · งานน้อย)*
ปิดทันที + แถบ "Closed — Undo" 5–8 วินาที → กลับไป 1 ขั้นต่อรายการ (กดพลาดก็ย้อนได้ ไม่ต้องยืนยันทุกครั้ง) · ยังคง confirm สำหรับ **Cancel** (ต้องมีเหตุผลอยู่แล้ว)

**4.6 ทำเป็นชุด (Bulk actions)** *(ผลสูง · งานปานกลาง)*
ติ๊กหลายแถวใน qc_list → **Submit Fix (เพิ่มรูป/โน้ตเดียวกัน)** สำหรับ Officer และ **Close selected** สำหรับ QC · ใช้กับกรณีแก้งานชุดเดียวกันหลายจุด

**4.7 ป้ายสถานะ "แก้แล้ว รอ QC" ในตาราง** *(ผลสูง · งานน้อย)*
ไม่เพิ่มสถานะใหม่ (ฟอร์มกำหนดแค่ O/C/N) แต่แสดงป้ายรอง "Fix submitted" จากรอบล่าสุด (`bjc_date`/รอบ `fix`) + ชิปกรอง "Waiting for QC" / "To fix" ให้ Officer และ QC เห็นคิวของตัวเอง

**4.8 Pre-test: "ตั้งทั้งหมวดเป็น YES" + เลื่อนถึงข้อที่ยังไม่ตอบ** *(ผลสูง · งานน้อย)*
ปุ่มระดับหมวด (ยืนยันก่อน) + ปุ่ม "ไปข้อถัดไปที่ยังไม่ตอบ" · เมื่อ punch ที่เกิดจากข้อ NO ถูก Close ให้ถามเสนอเปลี่ยนคำตอบเป็น YES ในที่เดียว

**4.9 Draft อัตโนมัติ + คิวส่งใหม่** *(ผลสูงหน้างาน · งานมาก)*
เก็บฟอร์มที่กรอกค้าง (ข้อความ + รูปที่ย่อแล้ว) ใน IndexedDB; ถ้า Save ไม่สำเร็จเพราะสัญญาณ ให้ค้างในคิว "Pending upload" และลองส่งใหม่เมื่อออนไลน์ + แจ้งจำนวนที่ค้าง (เริ่มจาก draft ก่อน คิวเต็มรูปแบบเป็นขั้นถัดไป)

**4.10 ทางลัดถึง pack ที่หน้างาน** *(ผลปานกลาง · งานปานกลาง)*
QR code ต่อ pack (พิมพ์ติดหน้าปก pack) สแกนแล้วเปิด Test Package Detail หรือฟอร์มเพิ่ม punch ของ pack นั้นทันที + หน้า Home สำหรับ QC แสดง "pack ล่าสุดของฉัน"

**4.11 มุมมอง "พร้อมทดสอบแรงดัน" ใน Register** *(ผลสูงสำหรับ PM · งานน้อย)*
ชิป/ตัวกรอง "Ready for pressure test" (pre-test ครบไม่มี NO และไม่มี punch A เปิด) — ใช้ตรรกะ gate เดียวกับแท็บ Pressure test

## 5. แผนการทำงาน (Roadmap)

| ระยะ | เนื้องาน | ผลลัพธ์ที่วัดได้ |
|---|---|---|
| **0 — เตรียมความพร้อม** (ผู้ใช้ทำ) | รัน `sql/09`; ล็อกอินดูทุกหน้ากับข้อมูลจริง; สร้างบัญชีทดสอบ 4 role; ตัดสินใจ 3 เรื่อง (ขั้นสถานะ pack, แม่แบบ Pre-test, สิทธิ์ลูกค้า) | รายการสิ่งผิดปกติ ≤ 1 วัน |
| **1 — ลดขั้นตอนที่คุ้มสุด** (1–2 สัปดาห์) | 4.1, 4.2, 4.3, 4.5, 4.7, 4.8, 4.11 + ปิดค้าง QA (contrast ลิงก์, tab stop, label, `data_guide` guard) | ตำหนิที่ 2+ ใช้ ≤ 4 ขั้น; ปิด punch ≤ 2 ขั้น; Pre-test ≤ 8 คลิก/pack |
| **2 — แกน Pressure Test** (1–2 สัปดาห์) | Pressure Test Record + gate ล็อกจริง; ปรับตารางที่เหลือให้ตรงมาตรฐาน | เฟส 1 ของ roadmap ครบ ~100% |
| **3 — งานหน้างานเต็มรูปแบบ** (2–4 สัปดาห์) | 4.4, 4.6, 4.9 (draft), 4.10 (QR) ; My Tasks | งานแก้เป็นชุดได้ ไม่เสียงานเมื่อสัญญาณหลุด |
| **4 — เอกสารและรายงาน** | Dossier PDF, Excel ของรายงาน punch, นำเข้า Excel ในเว็บ, Audit Log, Profile/403/404 | ส่งเอกสารลูกค้าได้จากระบบ |

ทุกระยะจบด้วย: `php -l` + `node --check` → `qa-ux-tester` ตรวจรอบ → ทดลองหน้างาน (หัวข้อ 6) → ค่อยไประยะถัดไป

## 6. แผนทดลองใช้งานหน้างาน (Pilot / Usability Test)

**ผู้ทดลอง:** QC 2 คน · Officer 2 คน · (ถ้ามี) 1 คนที่ไม่เคยใช้ระบบมาก่อน · อุปกรณ์จริงของไซต์ (ถ้ามี 2 รุ่นขึ้นไป)
**ข้อมูล:** pack ทดสอบ 1 pack (ห้ามทดสอบบน pack จริงที่ส่งลูกค้า หรือใช้บัญชี/โปรเจกต์ทดสอบแยก)

**งานที่ให้ทำ (จับเวลา + นับการกด + ถามว่างงตรงไหน — ไม่ช่วยจนกว่าติด):**
1. บันทึกตำหนิ 1 จุด พร้อมรูป และ Category A
2. บันทึกตำหนิ 5 จุดใน Drawing เดียว
3. (Officer) หางานของตัวเอง แก้ ส่งงาน พร้อมรูป
4. (QC) หางานที่แก้แล้ว ปิด 3 รายการ ตีกลับ 1 รายการ
5. ตอบ Pre-test 30 ข้อ โดยมี 2 ข้อ NO แล้วดูว่า punch ถูกสร้าง
6. ปิด punch แล้วเปลี่ยนคำตอบเพื่อให้ pack "พร้อม"
7. ทดลองตัดสัญญาณกลางการบันทึก (โหมดเครื่องบิน) ดูว่าเกิดอะไรขึ้น
8. กลางแดด/ใส่ถุงมือ: กดปุ่มพลาดบ่อยหรือไม่ อ่านสีสถานะออกหรือไม่

**ตัววัดความสำเร็จ (เป้าเริ่มต้น ปรับหลังได้ข้อมูลจริง):**
- บันทึกตำหนิแรก ≤ 60 วินาที · ตำหนิถัดไป ≤ 30 วินาที (ไม่รวมเวลาถ่ายรูป)
- Officer ส่งงานแก้ ≤ 4 ขั้น · QC ปิดงาน ≤ 2 ขั้น
- ผู้ทดลอง ≥ 80% ทำงาน 1–6 สำเร็จโดยไม่ถามผู้ดูแล
- ไม่มีข้อมูลหาย เมื่อสัญญาณหลุด (หลังทำ 4.9)
- ผู้ใช้เห็นข้อความ error ภาษาคน 100% (ไม่มีข้อความดิบ)

## 7. กติกาออกแบบ เพื่อไม่ให้กลับมาซับซ้อน
- งานหลัก 1 อย่างต่อ 1 หน้าจอ; ของขั้นสูงซ่อนใน "More"/แท็บ (progressive disclosure)
- ค่าเริ่มต้นฉลาด (จำค่าล่าสุด/ค่าที่พบบ่อย) แทนการให้ผู้ใช้เลือกทุกครั้ง
- ปุ่มทำลายล้างไม่ได้ถูกวางใกล้ปุ่มหลัก; การกระทำที่ย้อนได้ใช้ Undo ไม่ใช้ confirm ทุกครั้ง
- ปุ่ม ≥ 44px · สถานะแยกด้วยข้อความ/ไอคอน ไม่ใช้สีอย่างเดียว · contrast ≥ 4.5:1
- ทุกหน้า: loading / empty (บอกขั้นต่อไป) / error (ภาษาคน) และใช้คำศัพท์ชุดเดียวกัน (ดู `project_status.md`)
- เปลี่ยนแปลง UI ที่กระทบวิธีทำงานต้องผ่านการทดลองหน้างานก่อนเป็นมาตรฐาน

## 8. ความเสี่ยงและข้อควรระวัง
- Bulk close/Submit เป็นการเขียนข้อมูลจำนวนมาก → ต้องมีสรุปก่อนยืนยัน + บันทึกว่าใครทำ (รอ Audit Log) และตรวจสิทธิ์ที่ RLS
- Draft/คิวออฟไลน์เก็บรูปในเครื่อง → ควรจำกัดขนาดและล้างเมื่อส่งสำเร็จ; อุปกรณ์ร่วมใช้ต้องล้างเมื่อออกจากระบบ
- QR code ต้องผ่านการล็อกอิน (ไม่เปิดข้อมูลสาธารณะ)
- การลดขั้นตอนห้ามทำให้ข้ามกฎฟอร์ม: Category A/B ยังต้องเลือก, Pressure test ยังถูกล็อกตามเงื่อนไข, สถานะมีแค่ Open/Closed/Cancelled
